> 历史记录：以下是 master 合并前的实现与验证条件。当前采用统一 RGB-D 流程、右臂观测和 100 次默认预算，仅保留 GPT 抓放集成用例；本文旧配置开关和检查命令不再适用。当前使用说明见 [L1 任务](l1_tasks.md)。

日期：2026-09-28；分支 `houym/L1_dev`。本次修复更新共用运动执行方式，任务几何和评分版本仍为 `l1-rigid-v1`，执行版本为 `cartesian_linear_v1`。

2026-09-29 集成更新：以下故障与原始验证记录属于合并前版本。当前逐点逆解改为 Lula，
保留插值、速度限制、桌面检查和关节跳变拒绝；详见 [分支集成记录](l1_integration.md)。

## 已定位的原因

用户回合 `L1-01_simulation_20260928T115322Z_9ec76578` 的首步要求 TCP 从约 `(0.410, 0.420, 0.446)` 移至 `(0.400, 0.060, 0.160)` m，并保留初始横向姿态。旧执行器求解一次 IK，直接发送末端关节目标；各关节的物理运动并不同步，运动中末端落到桌面附近。

最终 TCP 约 `(0.333, 0.173, 0.041)` m，位置误差 177.1 mm，第 4 关节误差约 1.444 rad，动作超时。张开指令因 `after_motion` 始终等待，实际夹爪约 41 mm，没有达到 70 mm。

首轮诊断中休眠后的接触读数为零；在独立诊断进程关闭参与臂休眠后，相同停滞位置测得 `link6` 对桌面的接触合力约 138 N，确认桌面阻挡。关闭休眠只用于定位，未写入正式运行配置，也没有提高驱动增益或力矩来强推。

## 修改后的执行条件

八项 L1 和四份 GPT 抓放任务配置共同使用：

```toml
[execution]
motion_mode = "cartesian_linear_v1"
gripper_timing = "open_before_motion"
startup_pose = "downward_ready_v1"
```

1. **分段执行指定目标。** 位置直线插值，姿态沿最短四元数旋转插值，每段不超过 10 mm / 5°。Lula IK 逐点以上一点为种子求解。参考速度上限为 0.10 m/s、0.5 rad/s，关节参考速度同时受原 R5 配置约束；跟踪落后时参考不继续前进。路径时间超过动作预算、IK 不收敛或关节分支跳变则整条动作拒绝。
2. **检查已知桌面。** 使用现有 R5 URDF 碰撞网格的保守包围盒与既有工作台范围，在动作下发前检查路径样本以及样本间的关节插值。预测穿入桌面超过 2 mm 会拒绝并报告连杆和原因。它不读任务物体位姿，也不规划绕过夹具的路线。
3. **明确开合顺序。** GPT 在组合命令中要求张得更宽时，保持机械臂当前关节位置，先执行并确认张开，再移动；闭合仍等运动到位并稳定后执行。纯夹爪命令即时执行。拒绝的组合命令不会执行其中的开合部分。
4. **取消超时动作。** 超时取消待执行的路径与延后开合，机械臂改为保持实测关节位置；随后空命令不会恢复这条过期路径。反馈记录取消状态，新的目标仍由 GPT 选择。
5. **澄清姿态和接近规则。** 提示明确 `sparse_eef` 的全零角度表示朝下、在 roll/yaw 为零时 pitch=-90 表示横向、三个 null 角度保留实测姿态；先选择观察／接近位姿、对准再下降。没有替 GPT 自动指定试管位置、抓取点或抓取朝向。

后续根据用户要求增加固定首步准备动作 `downward_ready_v1`：在现有 home 的 TCP 位置原地转向下无法满足 IK，因此沿同一执行器移动到相对基座 `(0.36, 0, 0.21)` m 的固定位置，同时将 TCP +X 转向世界 -Z。当前左臂对应世界 `(0.36, 0.42, 0.25)` m，夹爪开口不变。八项 L1 和四份抓放任务配置相同，不按物体位置调整。GPT 首次观测在准备成功后采集；准备失败不调用模型，记录为未评估任务。

`episode.jsonl` 分别记录 `preparation_start`、`phase=preparation` 和 `preparation_complete`。该动作消耗控制步和墙钟时间，但不计入模型决策或执行动作数量，也不产生抓取评分。将 `startup_pose` 改成 `none` 可关闭；需将这一条件与模型、执行器版本一起固定后才能比较结果。

在 2026-09-28 的修复中，传感器、模型服务、动作字段、R5 资产、当时的数值 IK、物理步长、驱动力矩、夹爪尺寸和评分器未因本修复改变。执行条件本身有变化，所以旧 `direct_ik / after_motion` 结果与新结果不能当作相同执行条件的模型能力比较。旧执行模式仍可显式配置，但当前 IK 为 Lula，完整复现旧版需检出合并前提交；既有基础关节／笛卡尔／抬手工程检查保留各自原配置。

`scene.json.motion_executor`、配置副本和源码哈希记录实际版本；具体逻辑在 `robots/motion.py`、`robots/adapters.py`，通用超时记录在 `runner.py`。

## 手动复测

在仓库根目录执行，Windows 使用 `python`：

```bash
# 无需 API；自动完成后退出，可查看 runs/ 中的 motion.jsonl、图片和结果。
python3 tools/launch.py check l1-motion --gui

# 使用已有模型配置，先在当前终端设置对应 API 密钥环境变量。
python3 tools/launch.py run L1-01 --gui
```

如果覆盖 `--config`，旧的本机 TOML 不会自动迁移，需核对以上三个执行字段。已有仿真进程也需要退出后重新启动才能加载新代码。`check l1-motion` 为了复现历史故障仍直接从 home 重放旧指令；固定准备阶段由正式 `run` 入口执行。

这是已知桌面的保守检查，不是完整避障规划：包围盒可能拒绝部分可行姿态，离散路径与实际跟踪也有误差；工件、夹具和持物后的碰撞需要 GPT 根据图像决定动作。IK 拒绝、误抓及恢复仍属于待评估的行为。Windows GPU 验证与完整多种子测评尚未完成。
